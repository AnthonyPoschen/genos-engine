# GI v2: meshes, two tracers, a surface cache and screen probes

Status: accepted as the direction on 2026-10-10. It supersedes [ADR 0008](0008-lighting-uses-radiance-cascades.md) and [ADR 0011](0011-occluders-use-a-sparse-camera-box.md) when phase 6 of the migration lands. Until then those two still describe the shipped code. The full design is [GI v2](../systems/gi-v2-design.md).

Most future assets are arbitrary meshes, not our analytic shapes. Lumen is the proven reference we learn from, not a blueprint: we copy its per-mesh SDFs, hardware ray queries, mesh cards and screen probes, and diverge where its choices cause pops, lag or ghosting. Each mesh gets a signed distance field and a set of cards at import. A software tracer walks mesh SDFs near a ray's start and a world-anchored far SDF beyond. A hardware tracer uses Vulkan ray queries on a BVH when the GPU has them. Both sit behind one interface, and everything above it is shared. Light is cached on mesh cards (the surface cache) and in world probes, and the final picture is gathered by screen probes on visible surfaces. Direct light is traced per pixel through the same tracer, with a light tree for many lights and cached shadow masks for static lights. Emissive surfaces, including parts of a mesh driven by the glTF emissive texture, factor and strength, light the scene through the cache (cards capture emission, so screen probes, world probes and bounce all see it). Small or bright emissive regions are extracted at import, per mesh and texture-aware, as area lights in the light tree for clean direct light and shadows, without counting them twice. Changing or switching emission is a light change handled by the layer model, never a geometry change.

We keep our own rules where Lumen is weak. What is stored never depends on the camera; the camera only orders the work. Each moving light has its own layer, so on, off and dimming are free. Moving objects carry their own cards and an object-space proxy, and static GI ignores them. One priority score picks the work, each update finishes, then blends once. Screen probes reuse visibility across frames, never averaged light, so there is no ghosting. Screen probes and world probes split by distance and never do the same work: screen probes trace only to a short range and read the surface cache; world probes answer the rest of each ray, feed the cards' bounce, never shade a pixel, and run only when a change touches them. Every cache publishes only finished values, blended once, and screen probe ray directions are fixed per probe, so the risk we trade Lumen's ghosting for, flicker from live updates, is closed by design and tested by `temporal_flicker.rhai` and `world_probe_role.rhai` on both tracers.

Lighting has a soft budget of about 200 MB of VRAM (about 10-20 MB today); Ultra may go over it if that buys speed. The budget is spent to make each pixel cheaper: cached static light, cached shadow masks, persistent world probes with pre-integrated irradiance, precomputed probe visibility and distance fields. No radiance history is kept.

The hardware floor starts from the Steam survey: the newest 80 % of users, which in September 2026 is the 2018-2019 class (Turing, RDNA 1, Intel Xe, Ryzen Vega APUs). Anthony extended it so Low is tuned for Pascal and Polaris too, with the GTX 1060 6 GB as the reference card and the RX 580 as its AMD equivalent (about 88.9 % of users). The floor is Vulkan 1.3, not 1.4, because Polaris on Windows stops at 1.3; a gpuinfo.org check found every required feature on both cards. `shaderFloat16` stays optional, shaders do not assume a subgroup size, and 3D textures stay within 2048. Minimum VRAM is 4 GB. Hardware RT is optional and chosen only when ray queries are present. macOS uses the software tracer. The Steam Deck is a target but untested. Building SDFs and cards at build time or at first load is a config option; the editor defaults to build time. The reference path tracer, compare and the regression scripts remain the quality gate, run on meshes and on both tracers.

**Rejected:** Keeping analytic shapes as the trace target. Hardware RT as a requirement (about a quarter of users and macOS have none). Software distance fields only (RT is 72 % of users and is faster and sharper). Copying Lumen wholesale. Lumen's temporal accumulation of radiance. Camera-centred clipmaps and camera-distance card resolution, which change stored light as the camera moves. Importance-sampled or per-frame-rotated screen probe rays (crawling noise). Readers that see in-progress cache updates. A pixel fallback that reads world probes directly. Shrinking caches on the floor preset; the floor card is short on compute, not memory. Ray tracing pipelines instead of ray queries. A third-party glTF, image or BVH crate.
